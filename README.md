# telega

Чат-сервер на Go: комнаты на WebSocket, аккаунты с сессией в cookie, история сообщений в SQLite.

## Возможности

- Регистрация и вход: пароли хранятся как bcrypt-хэши, токен сессии в HttpOnly cookie
- Комнаты: создание, список комнат с пользователями онлайн
- Сообщения в реальном времени через WebSocket, ответ на конкретное сообщение
- Индикатор «печатает...»
- Догрузка при входе: приходит всё, что написали с прошлого визита, а при первом входе — последние 10 сообщений
- Heartbeat: сервер пингует клиентов и отключает тех, кто перестал отвечать

## Запуск

Через Docker:

```bash
docker compose up --build
```

Или локально (Go 1.26+):

```bash
go run ./cmd/telega
```

Открой http://localhost:8082, зарегистрируйся и создай комнату. Чтобы переписываться, открой второй браузер (или окно инкогнито) под другим пользователем.

База создаётся в `data/telega.db`, миграции применяются при старте.

## Архитектура

```
браузер ──WebSocket──► readPump ──► Hub (один на комнату) ──► writePump ──► браузер
                          │
                          └──► SQLite
```

- **Одна горутина `Hub` на комнату.** Она владеет картой подключённых клиентов и единственная её трогает, поэтому мьютекс не нужен: остальные горутины общаются с Hub только через каналы (`register`, `unregister`, `broadcast`, `typing`, `list`). Hub запускается с первым клиентом и останавливается, когда уходит последний.
- **Две горутины на клиента.** `readPump` читает из сокета, сохраняет сообщение в БД и передаёт его в Hub. `writePump` отправляет то, что Hub кладёт в буферизованный канал `send` клиента, и пингует клиента. WebSocket-соединение допускает одного читателя и одного писателя одновременно — отсюда ровно две горутины.
- **Закладки прочитанного.** Hub запоминает последнее доставленное каждому пользователю сообщение и пишет закладки в БД пачкой раз в 5 секунд и когда комната пустеет, а не на каждое сообщение.
- **Паники** в горутинах и HTTP-хендлерах перехватываются и логируются, сервер не падает.
- **Хранилище:** SQLite через `modernc.org/sqlite` (чистый Go, без CGO), схема — миграции `goose` в `migrations/`.

## API

| Метод | Путь | Авторизация | Описание |
|---|---|---|---|
| POST | `/register` | — | `{"username", "password"}`, создаёт пользователя и сессию |
| POST | `/login` | — | `{"username", "password"}`, ставит cookie сессии |
| GET | `/me` | cookie | `{"username"}` текущего пользователя |
| GET | `/rooms` | cookie | `{"комната": ["кто онлайн"]}` |
| POST | `/rooms` | cookie | `{"name"}`, создаёт комнату |
| GET | `/ws?room=name` | cookie | WebSocket-подключение к комнате |

## Решения и известные ограничения

**Почему SQLite.** Один процесс и встроенная БД: ничего не надо ставить, всё запускается одной командой. Ограничения известны: SQLite блокирует весь файл на запись, а состояние комнат живёт в памяти одного процесса. Следующий шаг при росте — PostgreSQL и брокер pub/sub (например, Redis), чтобы несколько инстансов делили комнаты.

Осознанно принятые ограничения:

- Сообщения показываются в порядке, в котором их получил Hub, а не по `id` в БД. Два сообщения, отправленные почти одновременно, могут поменяться местами на экране; история после переподключения идёт в правильном порядке. Исправление потребовало бы писать в БД внутри Hub и сделало бы его узким местом.
- Закладка — одно число «прочитано до id» (watermark), и она двигается только вперёд.
- «Прочитано» значит «доставлено клиенту», а не «увидено пользователем».
- Закладки сохраняются раз в 5 секунд, поэтому после падения сервера пара сообщений снова покажется непрочитанной. Сообщения при этом не теряются.
